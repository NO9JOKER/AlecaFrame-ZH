# AlecaFrame 中文搜索原理（3.0.6 适配）

> 对应代码：`src/search.js`（bundle 末尾，由 `src/build.py:138-147` 在 `src/engine.js` 之后追加）
> 对应测试：`tests/search.test.mjs`（`node tests/search.test.mjs`）
> 参考实现：MIOEU `upstream/mioeu/alecaframe-zh-cn.js:362-800`（MIT）
> 最后核对：2026-11-07，本机 AlecaFrame **3.0.6**、Overwolf 0.311.1.6

---

## 0. 一句话原理

**中文不送给原生插件。** 输入含中文时，把查询 JSON 里的 `search` 清空，让插件返回该分类下的完整
JSON 列表，再用 `window.__AFCN_DICT__` 建的「中文 → 英文 / 英文 → 中文」双向索引在本地过滤，
把过滤后的 JSON 交给原来的回调。这是 MIOEU 的核心思路，本移植保留；变的是**钩子挂在哪里**
（见第 2 节，这是 3.0.6 与 MIOEU 最大的差别）。

> **顺序演进**：v1.0 本地过滤优先 → v1.1.5~v1.1.7 改为「英文改写优先」（当时误判为字段不匹配，
> 真实根因是 v1.1.6 修掉的 background charset）→ **v1.1.8 恢复本地过滤优先**，英文改写只作为
> 「本地 0 命中」的兜底。原因见 §3.1 末尾的实测案例：部分中文会被 UI 术语抢走。

## 1. 词典与索引（`src/search.js` 第 1 节）

输入：`window.__AFCN_DICT__`（英文 → 简体中文，~20k 条；`items.tsv` 18,778 条 + vendor UI 词库等）。

启动时建两份内存索引：

| 索引 | 内容 | 用途 |
|---|---|---|
| 正向 | 英文（原样 + 小写）→ 中文 | 把插件返回的英文物品名翻成中文，用于本地过滤与建议列表 |
| 反向 | 中文（小写）→ 英文数组（排序后） | 中文输入 → 英文查询词；市场建议点击时换 slug |
| 子串 | 中文键数组（排序） | 中文只输入一部分时的兜底 |

### 1.1 择词策略（同一条中文对应多个英文名）

实测 `dict/items.tsv`：18,778 条里 **15,569 个不同中文名**，其中 **812 个中文名对应多个英文名**
（例：`入侵者` → `Intruder` / `Invader`；`牺牲` → `Sacrifice` / `The Sacrifice`；
`兆力使姿势组` → `Ropalolyst Pose Set` / `Teralyst Pose Set`）。

固定策略（`buildIndex()` 末尾的排序 + `exactReverse()` 取 `[0]`）：

1. **英文名短的优先**（`a.length - b.length`）——短名是「整件物品」，长名多是它的部件/变体。
   例：`后纪 A1` → 候选 `Axi A1` / `Axi A1 Intact` / `Axi A1 Exceptional`… → 取 `Axi A1`。
2. **长度相同按字母序**——保证跨机器、跨词典顺序完全确定（可复现，测试覆盖）。
3. 候选桶本身按上述顺序排序，保留全部候选（`index.reverse` 可审计）。

### 1.2 部件组合反查（"杀格 Prime 枪管蓝图" → "Sagek Prime Barrel Blueprint"）

`englishForChinese()` 的查找顺序（每一步失败才走下一步）：

1. **整名精确**：`杀格 Prime 枪管蓝图` 在 `items.tsv` 里就有 → 直接命中。
2. **部件组合**：用 `PART_EN_TO_ZH`（**照抄 `src/build_items.py:39-51`**，避免与词典生成规则分叉）
   的中文部件做**最长**尾部匹配 → 剥出父名 → 父名走 2.1/2.2 解析 → `父英文 + 英文部件`。
   例：词典里没有整名 `Sagek Prime Upper Receiver`，但 `杀格 Prime 上机匣` = `杀格 Prime` + `上机匣`
   → `Sagek Prime` + `Upper Receiver`。最长匹配保证 `枪管组件`（Barrel Assembly）优先于 `枪管`（Barrel）。
3. **Prime 后缀**：中文 `X Prime` 只在词典里有 `X` 时 → `X` 的英文 + ` Prime`。
   （Warframe 名不译：`Excalibur Prime 机体` 这种父名保留英文，正是 `build_items.py:165-166` 的规则。）
4. **中文子串兜底**：取「中文名最短、再英文最短、再字母序」的候选。
5. 都不行 → 返回 `null`，**不猜**（调用方保持原英文查询，让 UI 显示「无结果」而不是错结果）。

反向同理：`toChineseName()` 先查整名，再按英文部件表（最长优先）拼中文，
最后 `X Prime` 只差基础名时保留 ` Prime`。

> 遗物精炼后缀（`REFINE_EN`/`REFINE_ZH`，`build_items.py:50-51`）在词典生成阶段已剥离，
> 所以中文搜索 `后纪 A1` 能命中 `Axi A1` / `Axi A1 Intact` / …（`items.tsv` 里这些英文名都映射到 `后纪 A1`）。

### 1.3 过滤规则（`filterItems()`）

- 按空白拆词，**每个词都必须命中**（AND）：`杀格 枪管` → 同时含「杀格」和「枪管」。
- 每个字段的可搜索文本 = `中文字幕名（小写） + " " + 英文原名（小写）` → 中英混输、英文搜索都成立。
- 物品名翻不出来（词典缺口）时只剩英文名参与匹配 → 中文查询不会误命中，也不会崩。
- 字段名随页面不同：库存/铸造 `["name"]`，WFM 合同/已揭示裂罅 `["weaponName","name"]`，
  遗物规划特殊（`normalData.name` + `custom.rewards[].name`）。
- **遗物奖励**：库存「遗物」列表的条目只有遗物名（`Axi I1`），没有奖励字段，中文搜索会漏。
  `window.__AFCN_RELIC_REWARDS__`（`dict/relic-rewards.tsv` → `src/build_relic_rewards.py` 生成）
  提供「遗物基础名 → 奖励中文名文本」，`filterItems()` 会把它拼进可搜索文本，所以输入「死亡」
  能命中含「死亡魔方」奖励的遗物；精炼后缀（`Radiant` 等）在查找前剥离。

## 2. 钩子挂在哪：3.0.6 的结构性发现

### 2.1 插件实例在 `background.html`，不在 `main.html`

| 证据 | 位置 |
|---|---|
| 插件对象由 background 页面创建 | `web/assets/js/background.js:1` `var plugin = new OverwolfPlugin("AlecaFrameWrapper", true);`（`OverwolfPlugin` 见 `sharedOverwolfStuff.js:17-63`） |
| 主窗口脚本从「主窗口」取插件 | `web/assets/js/main/mainBase.js:15` `var plugin = overwolf.windows.getMainWindow().plugin;`；`sharedOverwolfStuff.js:3-4` 同样写法 |
| manifest 里 background 是后台页 | `manifest.json` → `data.windows.BackGround.is_background_page = true`，`start_window = "BackGround"` |
| **上游自己就是这么绕的** | MIOEU 的中文 OCR 桥脚本注入 `background.html`，并在那里改写插件方法：`upstream/mioeu/alecaframe-zh-cn-relic-ocr.js:60-96`（`originalPlugin.get()`）与 `:378` `nativePlugin.SetNewRelicScreenshot = function(...)` |
| 本项目的可行性报告已记录该结论 | `docs/可行性评估.md:99`「在 `background.html` 注入桥接脚本，拦截 `window.plugin`」 |
| 我们的 bundle 确实注入 background | `repo/bin/AlecaFrame-ZH.ps1:25-36` 的 `$Pages` 含 `background.html`；本机 `web/background.html` 末尾已有 `<script src="assets/js/alecaframe-zh-cn.js">` |

**结论：插件级钩子在 `background.html` 里安装**（那里 `window.plugin.get()` 就是本地 C# 插件实例，
`main.html` 拿到的只是跨窗口引用）。这样 MIOEU 的「改插件方法」思路在 3.0.6 才真正落地。
`main.html` 同时也会注入本文件，负责**应用级**钩子（Vue 实例侧）。

> 状态：`background.html` 中「改写插件方法对主窗口调用生效」有 MIOEU OCR 的先例 ✅；
> 但**搜索钩子**的端到端效果还需要真机点一次搜索确认（见第 5 节自检方法）。

### 2.2 搜索框是 `<main-search>` 组件，`refresh` 读 Vue 数据而不是 DOM

| 选择器 | 宿主文件 | 关键事实 |
|---|---|---|
| `#inventorySearch` | `web/main_parts/inventory.html:24` `<main-search id="inventorySearch" v-model="search" @input="scheduleSearch()" @search="refresh()">` | 组件定义在 `assets/js/main/search.js:53-57`：`inheritAttrs:false` + `inputAttributes` + 内层 `<input v-bind="inputAttributes">`，所以 id 最终落在**内部 `<input>`** 上；但 `inventoryApp.refresh` 读的是 **`this.search`**（`mainInventory.js:250-262`），不是 DOM value |
| `#foundrySearch` | `web/main_parts/foundry.html:13` `v-model="selectedSearch"` | `mainFoundry.js:139-146` 组装 `filterSettings.search = this.selectedSearch` |
| `#relicPlannerSearch` | `web/main_parts/relicPlanner.html:17` `v-model="search"` | `mainRelicPlanner.js:71-78` 组装 `filters.search = this.search.trim()` |
| 裂罅武器搜索 | `web/main_parts/rivenExplorer.html:90` `<main-search v-model="weaponSearchString">` | `general.js:183-193` 直接用 `this.weaponSearchString` 调插件 |
| 市场搜索框 | `web/main_parts/marketQuotes.html:10-15` `searchSuggestions` 列表 | 输入框绑定 `wfmSearchCurrentGuess`（`marketQuotes.js:11,125-142`） |

**因此 3.0.6 不能照搬 MIOEU 的「改 `input.value` 再调 `originalRefresh`」**（`alecaframe-zh-cn.js:473-509`）：
那条路径假设 refresh 从 DOM 读搜索词（jQuery 时代成立），3.0.6 读 Vue 数据，
改 `input.value` 只会让 v-model 的下一次渲染覆盖掉。本移植改为**从插件调用的 query JSON 里取 `search`**，
与 UI 实现解耦（哪怕以后搜索框改版也不影响）。

代价：搜索框里始终显示中文（体验正确），但库存/铸造的「结果计数 / 预估价值」汇总数字仍来自
「清空 search 后」的完整列表（见第 5 节风险）。

#### 为什么 v1.1.8 把「英文改写」从首选降级为兜底

反向索引是**词典全量**建的，里面混着 UI 术语，同一个中文可能先撞上术语而不是物品名。

实测（2026-11-07，本机 3.0.6）：`dict/mioeu-terms.tsv:769` 有 `Death -> 死亡`，于是

1. 用户在铸造厂搜「死亡」（想找「死亡使徒」= Kaszas）；
2. v1.1.5 的逻辑先做反向精确查找 → 得到英文 `Death`，直接交给原生搜；
3. 铸造厂里没有任何物品叫 `Death` → 原生返回 0 条 → 界面「无匹配物品」。

而同一份词典里「死亡使徒」→Kaszas 本来是本地过滤能命中的（中文含「死亡」的键共 39 个）。
所以顺序改成：**先清空 search 拿当前分类的完整列表，本地按中文名过滤**（支持部分中文、
只在当前分类内匹配）；**只有本地 0 命中时**才退回英文改写，交给原生再试一次。

## 5. 已知风险

1. **插件改写对主窗口是否生效 — 已真机确认**（2026-11-07 12:06~12:07，日志
   `%LOCALAPPDATA%\Overwolf\Log\Apps\AlecaFrame\BackGround.html.log`）：出现
   `钩子生效：GetWFMOrders:英文改写` 与 `钩子生效：getFilteredFoundry:英文改写`，
   证明 background.html 里对插件方法的改写对主窗口发起的调用确实生效。
   自检方法（游戏里打开 AlecaFrame，F12 控制台）：
   - `__AFZH_SEARCH__` 看 `hooks.plugin`（应为 8）与 `hits`；
   - 在库存/铸造搜索框输入中文，控制台应出现一次性 `[AFZH 中文搜索] 钩子生效：...`；
   - v1.1.8 之后中文查询应出现 `...:本地过滤`；若 `hits` 一直为空 → 跨窗口改写没生效。
2. **汇总数字口径**：库存/遗物规划的「预估价值 / 杜卡德 / 白金」由插件的 `ducatCount/platCount`
   原样透传，那是「清空 search 后的完整列表」口径，中文过滤后数字会偏大（MIOEU 同样问题）。
   若要精确，需要按过滤结果自行重算，依赖插件返回的价格字段，未做。
3. **性能**：中文搜索时库存会强制 `includeAll=true`，返回完整库存 JSON（可能数千条）；
   反查/子串是 O(词条数)（15k）级别，单次 < 数毫秒；过滤是 O(条数)。可接受。
4. **词典缺口**：`items.tsv` 没有的物品（部分是 Warframe 名、个别新物品）中文查不到——
   这是词典问题，不是搜索逻辑问题；`build-unmatched.txt` 可查。
