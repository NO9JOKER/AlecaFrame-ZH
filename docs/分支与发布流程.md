# 分支与发布流程

> 面向：维护者与贡献者。
> 原则：`main` 始终可构建、可发布；功能通过 `feature/*` 分支和 PR 合入；维护者手动合并并发布。

## 1. 分支模型

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 发布分支 | 只接受 PR 合入；不直接提交功能代码 |
| `feature/<scope>` | 单个功能/改动 | 从 `main` 切出；一个 PR 一个主题 |
| `fix/<scope>` | 缺陷修复 | 从 `main` 切出；同 PR 流程 |

不设置长期集成分支。分支名用小写英文 + 连字符，与 commit scope 保持一致。

## 2. 贡献流程

1. 从 `main` 切分支；
2. 实现 + 本地检查 + 真机验证（按 Tier）；
3. 提交 PR，附证据/未验证项/回滚方式；
4. 维护者的复核 AI 输出报告；
5. 维护者手动合并。

贡献者不直接推 `main`，不自行合并。

## 3. 本地检查

以下为目标命令（工具实现后）；工具尚未落地时，使用仓库实际存在的等价脚本，并在 PR 中记录。

```powershell
python tools\build.py
powershell -ExecutionPolicy Bypass -File tools\verify.ps1
node tests\runtime.test.mjs
node tests\rules.test.mjs
node tests\search-feature.test.mjs
```

工具尚未落地时，使用仓库实际存在的等价命令，并在 PR 中记录；不要伪造输出。

## 4. 真机验证

| Tier | 要求 |
|---|---|
| T0 | 构建 + 受影响界面截图（改文档可免） |
| T1 | 搜索/规则测试、golden、受影响界面 REAL、日志 |
| T2 | Start/Restore/Refresh/Toggle/Status 全流程、快照/还原 hash、回滚验证 |

REAL 证据必须由开发者本人执行；维护者抽检 T2。

## 5. 提交与合并

- 提交信息：`feat|fix|refactor|docs|test|chore(scope): 中文描述`；
- 一个提交只做一件事；
- 生成物不入库；
- 维护者用 merge commit 或 squash 合并，具体以 PR 为准；合并后删除 feature 分支；
- 新提交触发重新审核，不复用先前批准。

## 6. 发布

1. 维护者确认 `tools/verify.ps1 -Package` 全绿；
2. 提交 `VERSION` + `CHANGELOG`；
3. 在 `main` 的发布提交上打 tag（如 `v1.2.0`）；
4. 推送 `main` + tag；
5. release workflow 校验 tag==VERSION、tag 在 main 上，构建并上传 zip；
6. 本机用 Release zip 覆盖安装一次，跑 `Status` / `Restore` 抽检。

## 7. 回滚

| 场景 | 做法 |
|---|---|
| 合并后发现严重问题 | 新开 `fix/` 分支修复后重新合并；必要时 revert |
| 发错 tag | 删除本地/远端 tag，修正后重打；已发布的 Release 以追加新版本为主 |
| 本机部署损坏 | `还原-官方英文.cmd`；必要时从 `app.opk` 还原或重装 AlecaFrame |
| 用户端升级 | 用上一版 Release zip 覆盖安装，保留 `state/`、`logs/` |

## 8. 安全与合规

- 不修改官方签名/DLL；唯一允许的官方文件原地补丁是 OCR 相关文件，且必须可还原；
- 运行时会绕过 Overwolf 校验参数，发布说明中保留免责声明；
- 不把 token、账号、本机绝对路径写进仓库/证据。
