> 一句话：**main 永远保持可发布；所有更新先在分支上做，跑完 `scripts/verify.ps1` 且手动回归通过后，才合入 main 并推送。**
> 最后更新：2026-11-07（v1.1.7 之后引入）

---

## 0. 为什么要有这条流程

- main 上每次 push 都会触发 CI（`.github/workflows/build.yml`），打 tag 会触发发布（`release.yml`）；
  main 一旦坏掉，Releases 和「从源码更新」的用户都会受影响。
- 本项目的补丁与 Overwolf 校验参数、AlecaFrame 版本强相关，改错一个字符就可能让别人的 AlecaFrame 打不开。
- 所以：**分支上试错，main 上只放验证过的东西。**

## 1. 分支模型

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 可发布快照 | 只接受来自 `dev` / `feature/*` 的合并提交；不直接在 main 上改 |
| `dev` | 日常更新集成分支 | 小改动（词条、文案、脚本修复）先堆在这里，验证通过后整批合入 main |
| `feature/<主题>` | 单个较大改动 | 从 `dev` 切出，做完合回 `dev`；例如 `feature/relic-ocr-fix` |

命名建议：小写英文 + 连字符，主题与提交信息里的 scope 保持一致（`fix(search)` → `feature/search-fix`）。

## 2. 一次更新的完整流程

### 2.1 开工

```powershell
git switch dev
git pull --ff-only            # 有远端更新时执行；本机无网可跳过
```

大改动再从 dev 开 feature 分支：

```powershell
git switch -c feature/<主题>
```

### 2.2 改 + 构建 + 验证

```powershell
python src\build.py                                   # 改了 dict/ 或 src/ 才需要
powershell -ExecutionPolicy Bypass -File scripts\verify.ps1
```

- `verify.ps1` **必须全绿（exit code 0）**，否则不要提交合并；
- 只改文档时可以 `-NoBuild` 跳过构建；
- 要连发布包一起验：`-Package`；
- python / node 不在 PATH 时用 `-Python`、`-Node` 指定路径。

改完词条/脚本后，在中文会话里跑 `Refresh-Chinese.cmd` 看实际效果；改了启动器或页面清单则要完整 `Start` 一次再 `Restore` 一次。

### 2.3 提交

```powershell
git add -A
git commit -m "fix(search): 中文查询在 X 场景失效"
```

- 提交信息沿用现有风格：`feat/fix/chore/docs/refactor(scope): 中文描述`，发版提交带上版本号 `（vX.Y.Z）`；
- 一次提交只做一件事，方便回滚；
- 生成物（`bin/alecaframe-zh-cn.js`、`bin/ocr/afzh-items.js`）已在 `.gitignore` 里，**不要** `git add -f`。

### 2.4 合入 main（确认无误后）

```powershell
git switch main
git merge --no-ff dev -m "chore: 合并 dev（vX.Y.Z）"
python scripts\package.py                             # 可选：本地出包抽检
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin main
git push origin vX.Y.Z
```

- 发版前先改 `VERSION` 与 `CHANGELOG.md`（`verify.ps1` 会校验两者一致）；
- 推送 tag 后 GitHub Actions 自动构建并上传 `dist/AlecaFrame-ZH-vX.Y.Z.zip` 到 Releases；
- 推送失败先看第 4 节（git 与网络）。

### 2.5 发布后

- 在 Releases 确认 zip 大小与条目正常；
- 更新本机部署目录（见《维护手册》§9），跑一次 `Status.cmd` 和 `导出诊断包.cmd` 抽检；
- 版本号规则见《维护手册》§9.2（修词条 `v1.x.y`、加物品/规则 `v1.y.0`、适配新版 `v2.0.0` 级别）。

## 3. 验证门槛清单

`scripts/verify.ps1` 检查项与 CI 的对应关系：

| # | 检查 | 失败意味着 | 对应 CI 步骤 |
|---|---|---|---|
| 1 | `python src/build.py` 退出码 0 | 词条格式或构建脚本坏了 | Build dictionary |
| 2 | 产物含 `__AFCN_DICT__` 等标记 | 构建产物没生成/被截断 | Verify artifact |
| 3 | `dict/*.tsv` 每行都有 Tab | 词条会静默失效 | Check dict files |
| 4 | 所有 `.ps1` 为 UTF-8 with BOM | PowerShell 5.1 下中文乱码 | Check PowerShell UTF-8 BOM |
| 5 | 所有 `.ps1` 语法解析通过 | 启动器改崩了 | （CI 无，新增） |
| 6 | `node --check` 全部 JS | 注入脚本会 `Uncaught SyntaxError` | Syntax check JS |
| 7 | `node tests/search.test.mjs` | 中文搜索逻辑回归 | Run search tests |
| 8 | `VERSION` 与 CHANGELOG 首行版本一致 | 发版号对不上 | （CI 无，新增） |
| 9 | 生成物未被 git 跟踪 | 仓库会被构建产物污染 | （CI 无，新增） |
| 10 | `-Package`：发布包自包含 | 用户端功能静默失效 | release.yml |

**本地 verify 是「推送前」的门槛，CI 是「推送后」的兜底。** CI 暴露的新问题要补进 `verify.ps1`，避免犯两次。

## 4. git 与网络（本机实测，2026-11-07）

- 命令行可能没有 `git`（不在 PATH）。可用 GitHub Desktop 自带的 git：
  `%LOCALAPPDATA%\GitHubDesktop\app-*\resources\app\git\cmd\git.exe`。
- 推送走 HTTPS 出网：本机直连失败时先确认代理（Clash 默认 `127.0.0.1:7897`），
  然后 `git -c http.proxy=http://127.0.0.1:7897 ...`。
- 如果 git 报 `schannel: AcquireCredentialsHandle failed`，改用 OpenSSL 后端：
  `git -c http.sslBackend=openssl ...`（本机用这个组合可正常访问 GitHub 公共仓库）。
- 本仓库为私有仓库时，push 需要 GitHub 凭据；用 GitHub Desktop 登录过的账户即可复用。
  沙箱/受限环境下凭据助手可能起不来，此时最稳的是用 GitHub Desktop 客户端点 Push。

## 5. 回滚

| 场景 | 做法 |
|---|---|
| main 上刚合入还没推送 | `git reset --hard origin/main`（本地丢掉合并） |
| 已推送但发现严重问题 | 新开 `fix/` 分支修复后重新合并；紧急时 `git revert -m 1 <merge-commit>` 再推 |
| 打错 tag | `git tag -d vX.Y.Z` + `git push origin :refs/tags/vX.Y.Z`，修好后重打 |
| 本机部署坏了 | 维护手册 §8.2 三层回滚（Refresh → Restore → opk 手动还原） |

> 已发布的 tag 尽量只「追加新版本」，不要重写历史；删 tag 会让已经下载的用户指向不存在的版本。
