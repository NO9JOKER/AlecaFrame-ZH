# AlecaFrame 简体中文适配可行性评估报告

- 评估对象：AlecaFrame（Overwolf 应用）本机版本 **3.0.6**
- 运行平台：Overwolf **0.311.1.6**（本机另存 0.311.0.6）
- 评估日期：2026-11-04（Asia/Shanghai）
- 目标拆解：①界面全面汉化 ②开核桃（开启虚空遗物，下称"遗物"）中文 OCR ③紫卡（裂罅MOD）中文 OCR ④与 warframe.market 的中文联动
- 取证方式：本机只读取证 + 上游社区实现源码 + 官方文档/条款 + 直接调用 warframe.market API + Warframe 中文 Wiki
- 证据等级：✅ 有实证（本地一手/官方原文/API 实测）｜⚠️ 间接依据（第三方实现、二手转述）｜❌ 查不到

## 0. 一页结论

| 目标 | 可行性 | 结论 | 主要依据 |
|---|---|---|---|
| ① 界面全面汉化 | **可行，但必须绕过平台校验** | 前端未混淆、有现成 1,104 条词库与注入方案；但每次启动要关 Overwolf 扩展完整性校验，且每版需回归 | 本地 `web/` 为可读 HTML/JS；社区补丁与启动器源码 ✅ |
| ② 开核桃（遗物）中文 OCR | **技术可行，但时机不佳** | 社区已用 PaddleOCR + 本地桥接做出中文遗物识别；但官方语言兼容表已把中文 Relic Rewards overlay 标为"⏲️ will be available soon" | 上游 OCR 管道源码 ✅；官方 docs 语言表 ✅ |
| ③ 紫卡中文 OCR | **未解决，自研风险最高** | 官方紫卡 overlay 明确仅英文；社区中文紫卡 OCR 自述"仅诊断用、需真实中文重洗卡样本"；中文词条→英文市场词条还要做映射 | DLL 字符串、官方语言表、上游源码注释 ✅ |
| ④ warframe.market 中文联动 | **可行，但要"中文显示 + 英文查询"两层** | API 物品数据只有英文（3,893 条 i18n 全部仅 `en`），但 `gameRef` 就是游戏内 uniqueName，可与本地 14 语言名称表（含简中 19,511 条）关联 | API 实测 ✅；本地 lang.json 解析 ✅ |

**一句话结论：** 技术上"能打"，社区甚至已有两代开源实现；但这不是"改个语言包"级别的补丁——它必须关闭 Overwolf 的安全校验（违反平台条款、随客户端更新失效），且最难的紫卡中文 OCR 至今无人做成。**建议分阶段：先只做界面汉化（3–5 人天）验证可行性；遗物 OCR 等官方；紫卡 OCR 暂不投入或改做独立工具。**

## 1. 事实基线（本机取证）

### 1.1 架构

- 安装位置：`%LOCALAPPDATA%\Overwolf\Extensions\afmcagbpgggkpdkokjhjkllpegnadmkignlonpjm\3.0.6\`
- 类型：Overwolf **WebApp**（`manifest.json`：`"type": "WebApp"`，`manifest_version: 1`）
- 前端：`web/` 下 37 个 HTML + 未压缩 Vue/原生 JS（例：`web/assets/js/main/modals.js` 58 KB 明文可读；官方 FAQ 也承认前端"未压缩未混淆"⚠️）
- 原生：`NET/AlecaFrameClientLib.dll`（1.38 MB，C# 插件，通过 `extra-objects` 暴露给 JS）
- 页面（manifest windows）：`main`、`relicOverlay`、`relicRecommendation`、`rivenOverlay`、`InGameNotification`、`tradeFinishedNotification`、`AFBuilds`、`SquadMakingMain`、`SquadMakingSquad`、`arbitrationLive` 等
- 结论：改前端文案**不需要**动 DLL、签名或 opk（上游补丁同样如此），技术门槛低于"逆向客户端"。

### 1.2 语言现状

- **UI 文案是硬编码英文**：全目录检索无 i18n/词典/语言切换机制（`lang`/`i18n`/`locale` 命中极少，且都不是本地化框架）；`web/main_parts/settings.html` 内没有界面语言选项。
- **游戏数据本身已含简中**：`%LOCALAPPDATA%\AlecaFrame\cachedData\json\lang.json` 为 **19,511** 个 uniqueName × **14** 种语言（de/es/fr/it/ja/ko/pl/pt/ru/tc/th/tr/uk/**zh**），合计 273,154 条名称；例如 `GrnBannerScarfItem` → `zh: 战败旗帜`、`tc: 戰敗旗幟`。
- 但主数据表（Relics 3,208 条、Components 2,225 条等）本身是英文名，中文名要靠 uniqueName 关联 `lang.json` 才拿得到。
- 本机 `lastLang.tmp` = `zh`，说明 AlecaFrame 已按游戏语言识别到简体中文（DLL 里也有 `GetWarframeLanguage` 逻辑）。
- **官方语言兼容表（2026-11-04 抓取）**：中文列中 Foundry/Inventory/Mastery/Relic Planner/Rivens/Warframe.Market 均 ✅；Stats/Trading Analytics ⚠️（不记录交易历史）；**Relic Rewards overlay ⏲️ "Will be available soon"**；Relic Recommendation 🚫；Chat Riven / Riven Reroll 🚫（仅英文）。
- 冲突需并列：官方 FAQ 旧表述"暂时必须把游戏语言设为英文"，与上表"多个中文 tab 已 ✅、遗物奖励即将支持"存在张力（⚠️ 两条都是官方页面）。

### 1.3 OCR 在哪里、支持哪些语言

- 遗物/紫卡 OCR **不在前端**，在 C# 插件 + AlecaFrame 服务端：
  - DLL 字符串：`Submitting image for OCR`、`Sending OCR images to server...`、`Final OCR server response:`、`OCR Upload start!`、`Parsed OCR result:` —— 截图上传服务端识别。
  - 语言门禁（DLL 原文）：`Unsupported Warframe language detected. For the time being, only English, French, Spanish and German are supported.`（与官方文档"俄语 ✅、中文 ⏲️"不完全一致，⚠️ 以实际版本行为为准）
  - 紫卡门禁（DLL 原文）：`RivenSelectedForRerollDetected cancelled because the game is not in English.`、`Not opening relic recommendation because the game language is not supported.`
- 官方文档语言表：中文遗物奖励 overlay "即将支持"；紫卡相关 overlay 明确仅英文。**这意味着：中文环境下，官方 OCR 链路目前是缺的，前端注入无法"翻译"官方识别结果，必须自己造一条 OCR 链路。**

### 1.4 平台完整性校验与更新节奏（决定"补丁能不能活"）

- `_metadata\verified_contents.json`：**345** 条 SHA-256（312 条 `web/*`、29 条 `NET/*`、3 条根级含 `manifest.json`/`.git`/`.gitignore`）+ `global` 聚合哈希 + RS256 JWT 签名。
- 本机实测：**345/345 个文件哈希全部匹配**（说明当前是未被修改的官方状态）；改任一文件即 `HashMismatch`。
- 社区启动器实现（上游源码）正是靠匹配 Overwolf trace 日志判断被拒：`Closing extension '<appId>' - '(HashMismatch|InvalidSignature|MissingFile|MissingData)'`，并被要求"先让官方文件过校验、再注入、再只重启 AlecaFrame 渲染进程"。⚠️（第三方实现，但可解释其为何这样设计）
- 绕过方式（非官方、无文档 ✅本地可验证字符串存在）：启动参数
  - `--ow-disable-features=extension-validation,read-opk-from-memory`
  - Overwolf 0.311 起还需 `--ow-enable-features=force-validation-report-only`（把"校验失败=拒绝加载"降级为"记录差异继续加载"）
  - 本机 Overwolf 0.311.1.6 的 `Overwolf.Extensions.dll` 中仍能检索到 `extension-validation`、`read-opk-from-memory`、`force-validation-report-only` 三个字符串（✅），`ow-disable-features` 在 `OverWolf.Client.CommonUtils.dll` 中 —— 说明机制在当前客户端仍存在，但**未被官方文档化，随版本可能消失**。
- 更新节奏（本机观察）：
  - AlecaFrame 3.0.5 目录时间 2026-10-25 23:29 → 3.0.6 为 2026-10-26 12:17，间隔 **12.8 小时**（calc 复核）。
  - Overwolf 在 10-26 还是 0.311.1.1，11-04 已是 0.311.1.6；本机同时存在 0.311.0.6（11-03）目录。
  - 结论：**应用/客户端都在高频更新，任何"改文件"补丁都需要持续跟进。**

## 2. 四个目标逐项评估

### 2.1 界面全面汉化

**可行性：可行（技术难度中等），但维护成本高。**

- 落点：10 个 HTML 页面的 `</body>` 前追加 `<script>`；一个运行时翻译层遍历文本节点/属性并替换，配合 MutationObserver 处理 Vue 动态渲染。上游已证明可行（2.6.x）。
- 词库规模实证：上游 `translations.zh-CN.json` 共 **1,104** 条；本机扫描（只读）得到 HTML 静态文本节点 **1,258**、Mustache 节点 **796**、JS 字符串文案候选 **1,206** 条短语 + **614** 个单词、模板插值 **11**，合计候选节点 **3,885**（[ui_scan.json](recon/local/_tools/ui_scan.json)，含大量重复/开发用字符串，去重后估计 800–1,500 条可翻译文案）。
- 质量提醒：上游词库有明显机翻痕迹，例：`(Optional)` → "（选修的）"、`A player joined the squad` → "一名球员加入了球队"（球员=ball player）、`A player was kicked` → "踢出球队"（应译"玩家"）。**要做到"好用"而不是"能看"，需重新校订 1,000+ 条文案。**
- 字体/布局：包内字体 Beaufort/Roboto/Spiegel 均无 CJK 字形，浏览器会回退系统字体（观感尚可）；中文变长导致的换行/截断需要逐页目检（尤其侧栏、表格、按钮）。
- 预期工作量（估算，非实测）：移植到 3.0.6 并调通 **3–5 人天**；每次 AlecaFrame 大版本回归 **0.5–2 人天**（新增/改动文案）。

### 2.2 开核桃（遗物奖励）中文 OCR

**可行性：技术可行，且上游已有完整实现；但官方即将支持，自研的"保质期"存疑。**

上游实现（[alecaframe-relic-ocr.js](recon/upstream/alecaframe-zh-cn-relic-ocr.js)、[alecaframe-relic-ocr-server.js](recon/upstream/alecaframe-relic-ocr-server.js)、[alecaframe-paddle-reward-worker.py](recon/upstream/alecaframe-paddle-reward-worker.py)）：

1. 在 `background.html` 注入桥接脚本，拦截 `window.plugin`（C# 插件）的 `SetNewRelicScreenshot` 与 `overwolf.media.takeWindowsScreenshotByName`/`takeScreenshot`；
2. 把截图 POST 到本机 Node 服务 `http://127.0.0.1:38147/process*`，由 Python PaddleOCR 中文模型识别；
3. 用中文名→奖励条目的索引（`PADDLE_TRANSLATION_INDEX`：本地化名 + 英文名双索引）做纠错与匹配；
4. 结果回灌给遗物奖励 overlay 与遗物推荐 overlay（`publish-reward`），并写审计日志。
5. 前置组件安装脚本会把 Python、Node、PaddlePaddle、PaddleOCR 与中文模型装进项目 `.tools`（不改系统环境）。

技术障碍与风险：

- 依赖截图坐标/分辨率/HUD 缩放；上游为此专门做了"兼容性诊断报告"工具，说明适配面较广（多分辨率、HDR、超宽屏等）。
- 本地常驻 OCR 服务有额外 CPU/内存开销；上游 README 也承认"粗暴添加可能造成额外性能开销"。
- **官方语言兼容表已标中文遗物奖励 overlay "will be available soon"（官方服务端 OCR 在扩展语种）**——如果只等 1–2 个版本，自研 OCR 可能立刻过时。
- 预期工作量（估算）：把上游中文遗物 OCR 移植到 3.0.6 并调准 **3–7 人天**（含 PaddleOCR 安装、坐标标定、词表匹配调参）。

### 2.3 紫卡中文 OCR

**可行性：未解决；这是四个目标里最难、性价比最低的一块。**

- 官方口径：Chat Riven / Riven Reroll overlay 仅英文（语言表 🚫）；DLL 明确"游戏不是英文就取消重洗检测"。
- 上游 fork 虽然加了"中文紫卡 OCR"，但其服务端注释写得很直白：
  > "Riven OCR is diagnostic-only until a real Chinese reroll card sample has been captured and its line layout has been validated."
  即：**只做到诊断/截图采集，尚未达到可用**。
- 要做成需要三件事同时成立：
  1. 中文紫卡卡面的版面/字体/词条切分样本（需要大量真实截图）；
  2. 中文词条名 → 游戏内部属性 ID → **warframe.market 英文词条标识** 的映射（如 暴击几率 → Critical Chance → `critical_chance`）；
  3. 武器中文名 → 市场武器 slug 的映射（DLL 内有 `ResolveWarframeMarketWeaponUniqueName`，说明官方已有 uniqueName→slug 逻辑，可复用思路）。
- 额外限制：warframe.market 的紫卡拍卖**搜索**接口对程序化请求不友好——本机实测 `POST https://api.warframe.market/v1/auctions/search` 返回 **400 `CSRF: Token is not present in the request header`**，说明裸调不可行，必须复用 AlecaFrame 自己的登录态/内部调用。
- 预期工作量（估算）：**2–4 周研究型开发，成功率中等**，且每次游戏 UI 改动都要重标定。

### 2.4 warframe.market 中文联动

**可行性：可行，本质是"中文显示 + 英文查询"的映射工程，而非语言支持。**

- API 实测（2026-11-04）：`GET https://api.warframe.market/v2/items` 返回 **3,893** 个物品，每个物品字段 `id/slug/gameRef/tags/i18n`，而 **i18n 里只有 `en`**（3,893/3,893）；加 `?language=zh-hans` 或 `zh-hant` 无效果；`/v1/items` 返回 403。
- 但 `gameRef` 就是 Warframe 的 uniqueName（例：`/Lotus/Weapons/Syndicates/PerrinSequence/Pistols/PSDualCestra`），与本地 `lang.json` 的键完全同域 → **可以零成本建立"中文名 ↔ uniqueName ↔ 市场 slug"三向映射**；AlecaFrame 自身的数据表也以 uniqueName 为主键（Relics/Components 等 3,208/2,225 条）。
- 因此：
  - 界面显示中文物品名：可做（读 `lang.json`）；
  - 用中文搜物品再查英文市场：可做（中文名→uniqueName→slug）；
  - 紫卡市场查询：受英文词条/CSRF 限制，需要自建映射并复用应用内登录态，成本最高；
  - 交易挂单/改价等写操作：直接复用 AlecaFrame 现有功能最稳，不要另起炉灶。

## 3. 方案对比与推荐

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 等官方** | 不折腾；关注官方语言表更新 | 零风险、零维护 | 未知等待期；UI 仍是英文（官方无 UI 多语言计划 ❌） | 只关心遗物 OCR 的人 |
| **B. 前端注入汉化（社区方案升级）** | 复用 MIT 词库/启动器，适配 3.0.6 + 0.311.1.6；按需加 OCR | 见效快、可回滚、不动 DLL/opk/账号数据 | 违反 Overwolf 平台条款；每次启动要从特殊快捷方式；每次更新要修；OCR 需自己维护 | 接受"折腾+条款风险"的个人用户 |
| **C. 独立中文助手** | 不改 AlecaFrame，自建工具：截屏 + 中文 OCR + 市场查询 + 中文界面 | 不碰平台校验，长期稳定，可分享 | 工作量最大（等于重做一个轻量 AlecaFrame）；无 AlecaFrame 的库存/账号同步 | 想要长期可用、甚至分发的人 |
| **D. 只做界面汉化（B 的子集）** | 只注入翻译层，不做 OCR | 风险面最小、维护量最小 | 遗物/紫卡 overlay 仍按官方能力（中文不可用） | 最推荐的第一步 |

**推荐路径：**

1. **先做 D（界面汉化）**：3–5 人天，验证 3.0.6 + 0.311.1.6 下注入链路是否仍成立；失败可一键还原（官方 opk 备份 + `Uninstall` 脚本）。
2. **遗物 OCR 不急着做**：官方已标注"即将支持"，先观察 1–2 个版本；若官方落地，直接用官方。
3. **紫卡 OCR 暂不投入**：上游都停在诊断级，官方明确仅英文，且市场接口有 CSRF 限制；若确实需要，建议走 C（独立工具，只读屏幕，不碰 AlecaFrame）。
4. 如果最终目标是"可分享/长期用"，优先考虑 C；B 类补丁注定是"追着更新跑"的消耗战。

## 4. 若采用 B：路线图、验收与回滚

**阶段 0（0.5 天）可行性验证（最小闭环）**
1. 备份：`Extensions\afm...\3.0.6` 整目录 + `PackagesCache\...\3.0.6\app.opk` + `_metadata\verified_contents.json`；
2. 记录基线：本机已确认 345/345 哈希匹配，可作回滚校验基准；
3. 用命令行带两个参数启动 Overwolf，确认 AlecaFrame 正常加载；
4. 只改 1 个页面（如 `relicOverlay.html` 加一行注释）→ 重载 → 看 trace 是否出现 `HashMismatch`；再按上游"先验证后注入"流程操作，确认能加载。
5. 验收：能稳定进入汉化状态；失败能 30 秒内还原。

**阶段 1（3–5 天）界面汉化**
- 移植 `translations.zh-CN.json` + 翻译 JS，按 3.0.6 页面清单注入（10 页）；
- 重译/校订明显机翻条目；逐页目检布局（侧栏、表格、弹窗、overlay）；
- 验收：主要页面无英文残留、无换行截断、无 JS 报错。

**阶段 2（可选，3–7 天）遗物中文 OCR**
- 安装 PaddleOCR 本地依赖；移植桥接脚本与 38147 端口服务；
- 标定 1080p/2K/超宽屏截图的奖励卡片区域；用中英文双索引纠错；
- 验收：连续 20 次开遗物识别准确率、单次耗时、CPU 占用可接受。

**阶段 3（不建议现在做）紫卡中文 OCR**
- 需要先采集 30–50 张真实中文紫卡（重洗界面/聊天链接）样本，再做版面切分与词条归一化；
- 词条→英文 ID 映射表需要覆盖全部紫卡词条与武器类型；
- 验收：识别 + 市场价查询全链路。

**回滚**：`Uninstall` 脚本会停止 Overwolf、从 opk/备份还原官方文件、删除注入脚本；任何时候都能恢复英文原版。

### 最终建议（给决策用）

1. **如果只是"自己看着舒服"**：做界面汉化（方案 D），3–5 人天可上线，接受"每次从专用快捷方式启动 + 更新后可能失效"。

4. **如果要分享给别人**：不要用 B；条款和更新维护都会反噬，做 C 或推动官方支持。
